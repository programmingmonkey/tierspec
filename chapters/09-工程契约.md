# 第 9 章 · 工程契约

## 遇到的问题

项目里总有一类规则，说起来就一句话，却很要紧：「React hooks 必须写在任何 `return` 之前」「时间一律按某个时区展示」「每个数据面板都必须声明加载失败时显示什么」。它们的共同点是：**看一眼代码就能判对错**。

这类规则通常散落在各处：设计规范里夹一条，后端约定里夹一条，某份活文档里又写一条。有的有测试或 lint 守着，有的只是文字；守着的那些，守卫还在不在、守的是不是这条，没人说得清。

## 理念

**能对着仓库现状判对错的工程不变量，单独立成「工程契约」：每条一个文件，每条都登记它的机器守卫；没守住的部分，明写「仅文字」。**

- **契约管「代码必须怎么写」，设计系统管「界面长什么样」**，两者平级，互不夹带（第 10 章）。
- **守卫要登记，而且登记要能被验证。** 只写「有测试守着」不够，要写清是哪个文件、哪一段，由自测来证明它还在。
- **「仅文字」不丢人，隐瞒才危险。** 明写哪部分没守住，读者就知道这部分只能靠自觉，也知道该补哪里。
- **按「谁能违反」分类**，不按「规则写在哪端的代码里」。

### 放在哪、怎么分类

```
contracts/
  README.md          写法、模板、守卫登记规则、自测查什么
  frontend/<名>.md   只有前端代码能违反的
  backend/<名>.md    只有后端代码能违反的
  shared/<名>.md     两端都能违反的（一端产出、另一端消费的口径，或两端各自都要守的约定）：只写一份
```

每份契约的 front matter 里，「适用」取值是「前端」「后端」「两端」之一，分别对应 `frontend/`、`backend/`、`shared/`，自测会检查两者对得上。

### 什么进契约，什么不进

| 进 | 不进 |
|---|---|
| 能对着仓库现状判对错的不变量：「每个 X 必须声明 Y」「不许直接用 Z」「W 只能从 V 取」 | 一次性的操作纪律（跑什么命令、按什么顺序）：放技能或运维文档 |
| | 视觉取值与视觉规范：放设计系统 |
| | 事故经过与实测记录：放事故记录或活文档，契约里只指过去 |

加一条契约，和加一条规则过同一道门槛：不显而易见、犯过、写得具体（第 4 章）。另外，这条规则原则上要能写成机器检查，哪怕暂时只有文字；从根本上判不了对错的，留在普通规则里。

## 怎么落地

### 一条契约长什么样

文件名就是契约名，一级标题与文件名一致。下面是 `contracts/frontend/hooks顺序.md`：

```markdown
---
适用: 前端
读取时机: 写或改 React 组件与自定义 hook
守卫路由: <前端包>/src/**
---

# hooks顺序

## 规则

React hooks 一律写在任何 `return` 之前，条件渲染用 JSX 表达式，不用提前 return 跳过 hook。

## 为什么

违反时的代价是整页白屏；而构建只做转译，类型检查也判不出这类控制流约束，只有 lint 能拦。

## 机器守卫

| 守卫 | 守哪一端 | 形态 | 拦截点 |
|---|---|---|---|
| `<前端包>/eslint.config.mjs#'react-hooks/rules-of-hooks': 'error'` | 前端 | lint | pre-commit、部署前检查、CI |

挡不住什么：依赖数组的检查（exhaustive-deps）刻意没开，不在守卫范围内。

## 例外登记

无（这条规则零豁免：违规时改代码结构，不加 eslint-disable）

## 改实现前读什么

eslint 配置的头部注释（为什么这条直接上 error 级）。
```

**五块必备**，标题照抄、每块不能空，没有就写「无」：

| 块 | 写什么 |
|---|---|
| 规则 | 第一段是**规则首句**，会被原样收进索引（见下）；其余正文跟在后面 |
| 为什么 | 当下成立的理由；事故经过只指向事故记录，不搬进来 |
| 机器守卫 | 守卫登记表，加一两句「挡不住什么」 |
| 例外登记 | 哪些地方被允许不守这条规则。例外最好声明在代码里（比如组件上的一个说明字段），这里只指过去，不在文档里另列一份 |
| 改实现前读什么 | 想改这条规则的实现之前要先读的东西：头部注释、回归测试、参考实现的路径 |

**front matter**：

- **适用**：前端、后端、两端，与所在目录对应。
- **读取时机**：改什么代码时要读这条契约，会进索引的「什么时候读」一列。
- **守卫路由**（可选）：暂存了哪些文件时，提交环节该跑这份契约的守卫，见下文。

**规则首句**要能被机器检查，所以给它定几条机械标准：是一段正文（不是列表、表格、引用、标题或代码块），以句号结尾，长度不超过一个上限（比如 400 字节）。「能判对错、能单独读懂」机器判不了，靠写的人和审查。

### 守卫怎么登记

- 一行一个守卫，四列：守卫、守哪一端、形态、拦截点。
- **守卫列写「路径#锚点」**。锚点是那个文件里的一段原文（导出名、用例名、lint 规则名）。自测会检查「路径存在、且包含锚点原文」，这样「文件还在、守的那段被删了」也能被发现。同一条规则由几个文件守着（比如两个前端包各有一份 eslint 配置），就登记几行。
- **形态与拦截点用固定取值**：形态是测试、编译期断言、lint、钩子段（git 钩子脚本里的某一段检查）、运行时断言之一；拦截点是 pre-commit、部署前检查、CI、运行时，可多选。
- **覆盖**：每个能违反这条契约的端，要么至少有一行守卫，要么有一行「仅文字：<哪部分没守>」。
- **回链**：形态是「测试」的守卫，文件开头要写出契约的路径。测试报错时，读的人能找回契约。
- **表下写「挡不住什么」**：一两句，说清这条守卫的边界。

### 索引：每端一份，生成，不手写

契约正文不直接送到 agent 手里，送的是索引：

- **每端一份索引**，都是带 `paths:` 的按路径规则文件（第 3 章）。前端索引的 `paths:` 指向前端代码，后端索引指向后端代码。
- 前端索引收 `frontend/` 和 `shared/` 里适用于前端的契约；后端索引收 `backend/` 和 `shared/` 里适用于后端的契约。`shared/` 的契约只写一份，但两份索引都收。
- 索引每条一行：契约名、读取时机、规则首句、守卫与拦截点。正文按需再取。
- 索引表是规则文件里一段**生成块**，用脚本从各契约文件生成；自测保证它和生成器的输出逐字一致（第 4 章「唯一受控的例外」）。

### 自测查什么

- **登记**：front matter 齐全，「适用」和所在目录对得上；五块齐全且不空；规则首句符合机械标准；每个守卫的路径存在且含锚点；形态与拦截点取值合法；覆盖成立；测试守卫有回链；写了守卫路由的，每个路径模式至少匹配到一个真实文件。
- **索引最新**：两份索引的生成块都和生成器输出逐字一致。
- **没有悬空引用**：仓库里写出的契约路径都真实存在。

自测挂进 pre-commit，改契约、改守卫文件、删守卫文件都会触发。

### 提交时跑守卫，新守卫先过影子期

「守卫路由」写的是一个或几个路径模式：暂存的文件命中了，pre-commit 就跑这份契约的守卫，不必每次全跑。写的是守卫判对错时要读的输入，比如被测模块、守卫所在的目录。

新接进提交环节的守卫，先过一段**影子期**：只警告、不拦，同时记日志。一段时间后复盘日志，确认它判得对、不拖慢提交，再转成真正拦截。一上来就拦，误拦一次，就会训练出「红了也不用管」的习惯（第 2 章）。

## 代价与适用条件

- 每条契约是一个文件，加上守卫登记和自测，单条成本不低。只给「犯过、而且原则上能机器判」的规则立契约。
- **自测只证明守卫存在、含锚点、有回链，证明不了守卫真的守住了规则。** 别把「有守卫」读成「安全」。
- 作者项目里，提交环节的守卫还在影子期内（2026-11 开始），转成拦截以后的效果还没有数据。
- 契约体系适合规则已经多到散落各处的时候。起步时，一份按路径规则加一两个 lint 就够了。

## 踩过的坑

### 工程规则混在视觉设计规范里

「某类面板的数据时效怎么判」「取哪一天的数据」这类工程行为规则，最早夹在视觉设计主规范里。主规范管的是界面长什么样，这些规则夹在里面不好找，也没有地方登记守卫。

**修法**：把这类规则从设计规范里迁出，立成工程契约，按路径送达到改前端代码的会话里；设计规范只留视觉部分，并指向契约。

### 只有 lint 拦得住的规则

上面示例里的 hooks 顺序，理由见它的「为什么」。这条规则确实出过整页白屏的事故，所以直接上了 error 级 lint、零豁免，并登记成契约，让 agent 改组件时先在索引里读到它。
