# 第 7 章 · 活文档与 spec 分开

## 遇到的问题

用 spec 驱动开发一段时间后，仓库里会堆满文档：PRD、spec、设计、任务、方案、复盘……agent 要回答「现在系统是什么样」时，很自然地去读这些文档。

问题是，它们大多写的是**当时打算怎么做**。上线时改过方案、后来又被别的需求改过一遍，文档都不会跟着变。agent 读到一份三个月前的 spec，会理直气壮地告诉你系统「应该」是那样。

反过来，真正描述现状的文档，如果没人维护，几周就过期了；过期的现状文档，比没有更糟。

## 理念

**文档分三类，身份不同，用法不同：**

| 类别 | 回答什么 | 例子 | 可以当现状信吗 |
|---|---|---|---|
| **活文档** | 现在是什么样 | 架构说明、数据模型说明、部署手册、指标口径表 | 可以：它随代码一起维护；和权威源冲突时让位于权威源 |
| **过程文档** | 当时打算做什么、为什么这样定 | PRD、spec、设计、任务、方案 | 不可以：它是一次变更的快照 |
| **事故记录** | 某条规则为什么存在 | 每份规则对应一份事故记录 | 不可以：它是历史 |

另有一类不在表里：代码知识图谱这类**自动生成物**，用法见下文「生成物：用前先看日期」。

再加一条：**权威源优先。** 活文档也只是导览。表结构以 schema 文件为准，定时任务以注册它的代码为准，规则以规则文件为准。活文档和权威源冲突时，信权威源，回头改活文档。

## 怎么落地

### 文档地图：agent 的第一张地图

在文档目录下放一份 `docs/README.md`，作为 agent 进文档库的入口。光放着还不够，agent 得知道要先读它：在入口文件的触发表里加一行「回答架构、现状问题之前 → 先读 `docs/README.md`」（第 2 章）。下面这些写法规矩，则用一份 `paths: docs/**` 的按路径规则送达。

地图里写三样东西：

- 一句话原则：哪些是活文档、哪些不是、冲突时信谁；
- 目录结构：每份活文档一行，写清它讲什么；
- **权威源对照表**：
  
  | 主题 | 权威源 | 活文档里的导览 |
  |---|---|---|
  | 数据表结构 | `schema` 文件 | 数据模型说明 |
  | 定时任务 | 注册定时任务的那段代码 | 调度时间线 |
  | 某次变更约定要做什么（意图） | 那次变更的 spec。它不回答「现在系统是什么样」，完工后现状看代码和活文档 | — |
  | 代码约定、git 流程 | 规则文件与技能 | — |
  | 部署流程 | 部署脚本与部署规则 | 部署手册 |

- 新增活文档时同时登记进地图，否则没人找得到它。这一条可以用自测守住：扫描文档目录，没登记的活文档就判红（和第 3 章守映射的自测是同一类）。

### 活文档只写现状

活文档回答「现在是什么样」，变更史一律在 git 里。所以：

- **订正不留痕。** 发现某句错了，直接改成对的，不写「本行原写 X，某日订正」。留痕夹在正文里，读者每读一节都得先读一遍「以前错成什么样」。
- **不设修订记录、更新日期、「最后核对于」这类节或页脚。** 它们只在有人想起来时才更新，结构上必然滞后，读者按它判新鲜度只会得出错误结论。
- **值得留下的教训，写成现在时的警告**：「别写成 X：会导致 Y」「不能用 A 判：因为 B」。带日期的实测数据照留，那个日期标的是实测时点，不是文档改了哪天。
- **已删除的功能不留墓碑段落。** 最多留一句「不存在，改用 X」，拦住照着旧笔记操作的人。
- **会漂的数字不写死**（表数、条数、行号）：写权威源名加现测命令（第 3 章）。

判据一句话：**删掉这句话，读者对「现在是什么样」的理解会变差吗？** 不会，它就属于 git log，不属于活文档。

### 改代码必同步文档

列一张**文档同步表**：哪类代码改动，必须在**同一个提交里**同步哪份活文档。例如：

| 代码改动 | 必须同步的活文档 |
|---|---|
| 改数据库 schema（增删表、改字段语义） | 数据模型说明 |
| 增删定时任务 | 调度时间线 |
| 新增一端、换技术栈、核心依赖大版本升级 | 架构说明 |
| 改部署、环境变量、CI 配置 | 部署手册里对应的章节 |
| 改指标的计算口径 | 指标口径表 |

- **为什么要在同一个提交里**：活文档一旦落后于代码，读者就只能把它当历史看，它也就不再是活文档了。
- **判据比表格更重要**：如果一次改动会让活文档里某句现有的陈述变成假话，就要同步，不必逐字对上表里某一行。
- **提交前自检**：把这张表当成提交前的检查项，命中了就在同一个提交里补文档。
- **机器只能提醒，不能判。** pre-commit 可以在「暂存了某类代码、却没暂存对应文档」时打一行警告；但哪句话变成了假话，机器判不出来，看到警告要真去看一眼。
- 不要往活文档区塞一次性的「开发完成总结」「测试报告」「部署计划」，它们是过程文档。

### 过程文档：完工即冻结

- spec 完工即冻结，写法见第 4 章「spec 是变更快照，不是活文档」。
- PRD 是意图来源，不是现状；转成 spec 之后，需求以 spec 为准（第 5 章）。spec 执行中发现的新事实回填 PRD 的确认事项；那套 spec 完工时，PRD 一并归档，之后不再改。
- 两者都可以入库、可以读，但读的时候心里要清楚：这是「当时打算」，不是「现在是」。

### 事故记录：规则的「为什么」

- 一份规则文件对应一份事故记录，同名。规则正文里只留一句「复盘见某某」，经过与证据放在事故记录里。
- 按日期追加，写成后不改，只允许在条目末尾追加「后续」。
- 它是历史，只在顺着规则里的指针过来时读，不拿来判断现状。

### 生成物：用前先看日期

代码知识图谱这类自动生成的东西，可以帮忙看跨模块关系，但它有生成时间，过时了也不会告诉你。用前先看生成日期；关键结论回源码或活文档核对。

还要防一种循环自证：如果图谱摄取了 spec，而 spec 又引用图谱，两者「互相印证」并不构成证据（第 10 章）。

## 代价与适用条件

- 活文档要跟着代码一起改，每个提交多花几分钟。起步时只维护两三份最常被问到的（架构、数据模型、部署），等出现「agent 照着旧说法做错了」再加。
- 触发表要按项目定制。表本身不重要，重要的是「改了代码，就问一句哪句文档变成了假话」这个习惯。

## 踩过的坑

### PRD 不入库，逼得 spec 把 PRD 整段抄进来

早期 PRD 放在不入库的私人目录里，agent 读不到。为了让 spec 能独立读懂，好几份 spec 只好把 PRD 的结论整段抄进需求文件。于是同一份结论有了两份副本，正是第 3 章说的、迟早会漂的那种。

**修法**：PRD 改为入库、可读，但身份不变：仍是意图来源，不是现状权威。spec 从 PRD 的定案速查改写，逐条标出处，不整段照抄（第 5 章）。
