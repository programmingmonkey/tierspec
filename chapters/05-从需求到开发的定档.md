# 第 5 章 · 定档

## 遇到的问题

Spec 驱动开发最常被诟病的，是它把每个改动都变成一场小型瀑布：改一个错别字也要先写需求、再写设计、再拆任务。于是两种结局：要么流程被嫌烦、慢慢被绕过；要么人跟着 agent 写了一堆没人读的文档。

反过来，完全不写，又会在真正复杂的改动上翻车：改到一半才发现影响面比想的大，或者一个撤不回的步骤已经执行了。

## 理念

**流程的轻重，跟着改动走。先花一点时间只读调研，把改动看清楚，再决定走多重的流程。**

TierSpec 按顺序问两层问题定档：

- **先看三条 C 档判据**：有没有撤不回的步骤？有没有要人反复拍板的取舍？需不需要留档审计？任一成立，就是 C，走完整流程。
- **都不成立，再问两个问题**：改法能不能一句话说清？影响面核实过没有？两个都是「能、核实过」，就是 A，直接改；否则是 B，写一份轻量计划。

顺序很重要：「删一列」改法一句话就说得清，但它撤不回，所以是 C，不是 A。

另外两条贯穿全章：

- **风险不定档，只加码。** 风险高的改动不一定流程重，但一定要在所定档位上加要求，而且大风险一票生效，不会被「改动很小」冲淡。
- **改动量不参与定档。** 判的是「要不要分步」，不是行数。一千行的机械改名可以是 A，一行的口径改动可能是 C。

## 怎么落地

### 第一步：判类型

| 类型 | 改的是什么 | 验证纪律 |
|---|---|---|
| 产品需求 | 用户能看到的行为要变 | 验证新行为，也验证相邻的旧行为没坏 |
| 技术改造 | 产品系统，用户看到的行为不变 | **先证明旧行为**，改完证明行为没变 |
| 缺陷修复 | 产品系统里原本就错的行为 | **先复现**：写一个在旧代码上失败的测试，再修 |
| 工程任务 | 研发体系：工具、规则、CI、脚本、agent 配置 | 验证门槛真的会拦、会放（负对照） |

依次问：改的是研发体系吗？原本的行为是错的吗？用户能看到的行为要变吗？同时沾两类的，按主要驱动归类，另一类的要求作为补充写进去。

### 第二步：只读调研，报四行

调研只读：不改代码，也不改仓库里的文件（复现用的临时脚本放在仓库外）。深度到能写出下面四行为止：

```
根因：……（产品需求、技术改造、工程任务写「目标」）
影响面：调用方、消费方清单，以及是怎么列出来的
同类：同一写法、同一口径还有哪些位置，怎么枚举的，每处怎么处置（缺陷修复必写）
改法：能一句话说清就写一句；说不清就写卡在哪
```

- 结论里涉及「多少行、什么值、有没有这种数据」的，查线上，不查本地（第 11 章）。
- 这次改动会推翻旧 spec、现有测试或旧决定里写定的行为的，在四行里写明推翻的是哪一条，等人点头。写进 spec 时逐条标出「新增 / 修改 / 废止」，并引用旧 spec 里对应的验收编号。
- 改错别字、改文案这类不改行为的，跳过调研，直接改。

### 第三步：定档

按表里**从下往上**判：先看 C 的三条，任一成立即 C；否则在 A、B 之间选。

| 档位 | 判据 | 产出 |
|---|---|---|
| **A 直接改** | 改法能一句话说清，**并且**影响面已在调研里核实过 | 不写文件；四行写进提交说明 |
| **B 轻量计划** | 改法说不清，或根因、影响面还要查 | 单个 `spec.md`：目标与不做、做法与步骤、记录 |
| **C 完整** | 任一：有撤不回的步骤；有要人反复拍板的取舍；需要留档审计 | 三份文件：`requirements.md` → `design.md` → `tasks.md`；产品需求尽量先出 PRD 配原型（第 6 章） |

「一句话说清」的标准：一句话能说清这次 diff 改了哪里、怎么改，**并且一个提交做得完、一次验证验得完**。要分几步做、每步各自验证的，算说不清。只列出要改哪些文件，不算说清。

「撤不回」的例子：删列、删表、改大表的列类型；没有快照的大量生产数据写入；对外发布后收不回的口径。有快照、能回滚的小范围写库，不算撤不回；但不论档位、不论风险，凡写生产数据都要走第 12 章的写入流程。

**谁定**：agent 推荐，人拍板。A 且风险小的，报完四行可以直接做；其余等人定。推荐 B 时直接附上草稿，一次回复同时定档和批准。

### 第四步：按风险加码

| 风险 | 包括 | 在所定档位上加的要求 |
|---|---|---|
| **小** | 可回滚，出错马上能看见 | 无 |
| **中** | 一般的数据库迁移（加列、加索引）；改数据口径或统计口径（数怎么算、列表选哪些、怎么排）；改门槛与护栏本身（git 钩子、CI、lint、部署脚本、监控告警、备份）；后台、定时、异步链路；外部数据源（接入、换源、限流、降级）；新增依赖或依赖大版本升级；网关、证书、域名 | 哪怕是 A，也先报推荐、等人说行。改门槛与护栏的，要真的触发一次来验证（负对照），不能只看脚本能跑 |
| **大** | 权限、鉴权；支付与付费；隐私；静默失败且波及多个消费方；对大表持锁或重写整表的迁移、需要停写的迁移 | 中档的要求全做，再加：动手前写清**改法、验证、回滚**三句，人批了再动；A 档把这三句原样写进提交说明；写生产数据的那一步不许裁剪（第 12 章） |

**必问名单**就是中、大两级，加上 C 档判据里的「撤不回」：哪怕改动小到看起来像 A，也先报推荐、等人说行。

### A 的提交说明

A 不写文件，证据全在提交说明里。第一行照常写一句话标题，空一行，再写四行：

```
<一句话标题：改了什么>

根因：……（或「目标：……」）
影响面：……（怎么列出来的）
同类：<命令或范围>，<处置>          （缺陷修复必写）
改法：<一句话>
测试：<测试名>，修复前失败、修复后通过   （缺陷修复必写）
证据：线上只读 <日期>，<结果>          （结论涉及数据时）
```

风险大的再加「验证」「回滚」两行。没有可测行为的（纯样式、纯文案），「测试」一行写「无：<原因>」，并写清人眼怎么验。

### B 与 C 的结构

先说目录约定：每个 spec 放在一个以主题命名的目录里；一个主题拆成多套 spec 时，主题目录下放一份「主题 README」，写总目标、拆分表与上线顺序。每份 spec 开头有一行状态，取值是「草稿 → 已批准 → 执行中 → 已完成」，另有「已搁置」。

**B：一个文件三节。**

```
spec.md
  1 目标与不做    原话或出处、至少一条「不做什么」、验收（每条一个判定，有失败路径的写错误路径）、要核实的口径与来源、待确认
  2 做法与步骤    任务，每个任务带「验证」
  3 记录          谁哪天定了什么、执行中的变更
```

**C：三份文件，每写完一份停下等人 review。**

```
requirements.md   1 背景与目标 · 2 范围（含至少一条「不做什么」） · 3 验收标准（编号，每条能判对错）
design.md         4 现状与方案（现状逐条标来源与日期；分期表）
tasks.md          5 任务 · 6 记录
```

- 「不做什么」至少写一条，给实现者划清边界，免得 agent 自己往里补。
- 需求写完，写作者先自查：每条验收是否只有一种判法，再扫一遍容易漏的维度：非功能（性能、可靠、可观测、安全与隐私）、外部依赖失败时怎么办、术语前后是否一致、完成信号能不能测、有没有残留的占位符和模糊词。
- 人说「继续写下一份」，算上一份通过。三份都过了再请批；批准单独一个提交，然后才能开工。
- **都先写需求，不先写设计。** 产品需求的歧义，已经在 PRD 的确认事项里一轮轮问清了（第 6 章）；技术类的 C 档不另设「澄清问题」环节，歧义写成明确的假设，交给人 review 兜住。B 档拿不准的写进「目标与不做」里的「待确认」，每条带默认做法。
- **规模与分期**：可执行任务超过 20 个停下想想，超过 40 个必须拆成多套 spec。按「能独立上线、独立验证」纵切，不按「先建表、再写接口、再补测试」横切。分期表里每个阶段都要写「能不能独立上线」，并答得出「谁来验、验什么」。

### 执行中复核

定档不是一次性的。在三个时点，对照当初的四行再问一遍：开工核实前提之后；测试跑出反例、或者试跑结果与预期不符时；每次记录变更时。

- 改法还能一句话说清吗？影响面还是调研时那些吗？有没有冒出撤不回的步骤、或要人拍板的取舍？
- 任一答案变了，停下报人，重新定档（A 发现说不清了，改走 B）。
- 风险级别变了，档位不一定变，但要按新级别补上加码要求。

### 完工验收

- 写作者在声称完工之前，对照验收逐条重跑验证，附上这一次跑出来的结果，不拿开发过程中某次跑过的结果代替。
- 人要求时，派一个**没参与执行**的审查员做完工验收：它只读需求、记录节和这套 spec 的提交，逐条给出在当前代码上重跑的证据。结论不能大于证据：没跑到的就写没跑到。
- 完工验收时，审查员可以跑测试、类型检查、构建这类验证命令；其他会写入或改变状态的命令照样不跑（第 7 章的审查员定义）。

### spec 是变更快照，不是活文档

完工后 spec 冻结：之后发现的问题追加在记录节，不回头改正文；要改行为就开新 spec。「现在系统是什么样」去看代码和活文档（第 8 章）。

### 只查结构的 lint

spec 的格式用一个小 lint 守住，挂进 pre-commit：任务行与编号格式对不对、状态是不是合法的几种、有没有任务节、任务有没有「验证」。**只查结构，不查内容**：内容对不对，靠写作者自查和人的 review。

## 代价与适用条件

- 「先只读调研」要花时间，小改动上会显得多余。但正是这一步，把大多数改动定成了 A：调研之后能一句话说清，就不用写任何文件。
- 定档要人参与。如果人总是回一句「你看着办」，档位就退化成 agent 自己说了算，风险加码里「等人说行」那几条也就失效了。
- 档位的判据可以按项目调整，但两个问题和「风险只加码」的结构建议保留。

## 踩过的坑

### 规范本身膨胀到没人读得完

旧的 spec 规范一路打补丁，长到 37KB，一次读不完，成了「名义上要遵守、实际没法通读」的文件。

**修法**：重写成不依赖特定工具、任何 agent 读普通 markdown 就能照做的精简版，约 7KB，配一个只查结构的小 lint；旧规范降级为存量专用。坦白说，它后来又随实践慢慢长回来了，到 2026-11 已经约 69KB。所以光重写一次不够：每长一次，都要按第 4 章的增删门槛过一遍。

### 格式 lint 静默失效了四次

曾经有一个检查 spec 任务格式的 hook，被当作唯一的强制兜底，结果先后四次静默失效，每次都没有任何信号。详见第 2 章「护栏存在 ≠ 护栏生效」。

**修法**：lint 换成一个独立脚本，挂进 pre-commit，自带正例、反例和控制组的自测。

## 依据与对照

### 和 Claude Code 官方最佳实践的对应

TierSpec 的很多做法，和 Claude Code 官方文档里的建议是同一个方向。下表对照的是 2026-11 读到的三页官方文档：[Best practices](https://code.claude.com/docs/en/best-practices)、[Memory](https://code.claude.com/docs/en/memory)、[Common workflows](https://code.claude.com/docs/en/common-workflows)。左列是官方的建议（括号里是「页名 · 原文小节名」），右列是 TierSpec 的对应做法。

| 官方建议 | TierSpec 的做法 | 详见 |
|---|---|---|
| 还没想清楚要什么的时候，先和 Claude 头脑风暴：让它访谈你，直到能写出 spec，写进 SPEC.md，再开一个新会话按它来实现（Best practices · Brainstorm with Claude first） | C 档产品需求尽量先出 PRD：人写骨架，agent 补全并把歧义列成待确认，逐轮答复；定案后转成 spec，按 spec 执行 | 第 6 章 |
| 改动落盘之前先看计划，用计划模式（Common workflows · Plan before editing） | 动手前只读调研、报四行，由人定档（A 档且风险小的可以报完直接做）；B、C 档把计划写成文件，批准后才执行 | 本章 |
| 给 Claude 一个能跑出「通过 / 失败」的检查，并要它拿出证据：只说「测试都过了」说明不了什么（Best practices · Give Claude a check to run） | 每个任务都带「验证」；完工时重跑并附这一次的结果；修缺陷先写一个在旧代码上失败的测试；数据类结论附上查询和查询时间 | 本章、第 11 章 |
| 让子代理对照 spec 审查，只报影响正确性的缺口，明确写上跳过风格问题（Best practices · Review against your spec） | 两路独立审查，提示里只报正确性问题和违背验收的问题，不报风格 | 第 7 章 |
| 区分确定性和非确定性的指令：每次都必须发生的事，做成 hook、deny 规则或托管设置（Best practices · Deterministic and non-deterministic instructions） | 同向，但 TierSpec 更保守：Claude hooks 判定器出错时会放行、模型也能改它，所以只算辅助；必须成立的事落到 git 钩子、lint 与测试、脚本门槛、CI 这些硬门槛 | 第 1、2 章 |
| CLAUDE.md 保持简短，每份目标 200 行以内（Memory · Write effective instructions）；只写 Claude 读代码得不出来的东西（Best practices · Keep CLAUDE.md short、Tell Claude what it can't see） | 入口只做地图；加规则先过「不显而易见、犯过、写得具体」三条门槛 | 第 3、4 章 |
| 局部规则用 `paths:` 限定范围；团队的多步流程放进技能（Best practices · Scope rules to one part of the codebase、Put team procedures in skills） | 按路径规则；多步流程做成技能 | 第 1、3 章 |
| 两次纠正都没纠正过来，就清空上下文、重写一个更好的提示，而不是再纠正第三次（Best practices · Steer the session） | 精神相近：执行中复核，改法说不清了就停下、重新定档，而不是硬着头皮往下做 | 本章 |
| 只读的审查子代理，把工具限制为 Read、Grep、Glob，由 Claude Code 强制（Best practices · Know what subagents cost） | 作者项目的审查员给了 shell，为的是看 git diff、查线上数据，代价是「只读」要靠约定；你可以按官方建议收紧 | 第 1、7 章 |

TierSpec 在官方建议之上多做了几件事：

- **分档。** 官方对还没想清楚的需求，建议访谈出一份 SPEC.md 再实现；TierSpec 对每个改动都先定档：A 档不写文件，B 档一份，C 档三份（产品需求尽量再加 PRD）。
- **风险加码。** 风险不决定写多少文档，但决定要不要先问人、要不要写回滚。
- **证据查线上。** 数据类结论不拿本地库当依据（第 11 章）。
- **审查要量化。** 用样本集比较审查流程改动前后的命中数（第 7 章）。

官方文档会更新，用的时候以你读到的现行版本为准。

### 和其它 SDD 方法的取舍

作者项目在 2026-09 重建 spec 体系时，对照了几个开源的 spec 驱动开发项目：[GitHub Spec Kit](https://github.com/github/spec-kit)、[OpenSpec](https://github.com/Fission-AI/OpenSpec)、[BMAD-METHOD](https://github.com/bmad-code-org/BMAD-METHOD)、[cc-sdd](https://github.com/gotalab/cc-sdd) 等，逐条记下采纳与否和理由。这些项目是由子代理抓取网页阅读的，引用的是转述，不保证逐字；它们之后也都可能改版。

**采纳的（代表项）：**

| 做法 | 出自 | 在 TierSpec 里 |
|---|---|---|
| 多数改动用轻量的 spec，渐进地严格 | OpenSpec（Lite / Full） | A / B / C 分档 |
| 一次改动要能一句话说清唯一的意图，需要很多「并且」就拆 | OpenSpec | 定档的「一句话说清」 |
| 需求至少写一条「不做什么」，免得下游自己补 | BMAD（v4、v6 两版模板）、cc-sdd | B 档「目标与不做」、C 档「范围」里至少一条 |
| 不确定的地方不许猜，要标出来 | Spec Kit（`[NEEDS CLARIFICATION]`） | 写明假设，或列进待确认、附默认做法 |
| 成功标准与技术无关、可度量 | Spec Kit | 验收「每条一个判定」 |
| 完工证据必须是当前代码状态下新产生的，结论不能大于证据 | cc-sdd | 本章「完工验收」 |
| 改动旧行为时，显式标出增、改、删 | OpenSpec | 逐条标「新增 / 修改 / 废止」，引用旧验收编号，等人点头 |

**没采纳的（代表项）：**

| 做法 | 出自 | 为什么不采纳 |
|---|---|---|
| 维护一份「当前规格库」，归档时把变更自动合并进去 | OpenSpec | 会和活文档形成两个「现状」的真源（第 8 章） |
| 单独一份「宪法」文件，带版本号和修订规则 | Spec Kit | 和规则文件重复，变成规则的副本（第 4 章） |
| 测试可选，只在需求明说时才写 | Spec Kit | 和「修缺陷先写失败测试」「任务都带验证」冲突 |
| 写需求前单设一个提问澄清的环节 | Spec Kit | 不另设环节，歧义写成假设或待确认；它的扫描维度（非功能、外部依赖失败、术语一致等）吸收进了需求的自查（见本章「B 与 C 的结构」） |
| 用户故事按 P1 / P2 / P3 排序、每条独立上线 | Spec Kit | 服务于多人分批上线；大需求已经按「拆成多套 spec」处理 |
| 项目记忆文件（产品、技术、结构、路线图） | cc-sdd 等 | 和常驻规则、活文档重复 |
| 任务写工作量估算 | spec-workflow-mcp | 对 agent 执行没有意义；规模用任务数阈值控制 |

作者项目还拿自己的旧 spec 做过一次回顾（子代理抽样打分，属于主观估计），结论也进了规范：用户故事只有不到一半带有效信息，所以默认不写，动机写进背景；EARS 句式（形如「当……时，系统应……」的需求写法）只在状态、时段、分支多的地方按需用。
