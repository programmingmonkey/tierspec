# 第 12 章 · 生产操作纪律

## 遇到的问题

个人项目里，开发和运维是同一个人。给了 agent ssh 和数据库权限之后，它能做的事和你一样多：查线上数据、改线上数据、部署、重启服务。

大多数时候这很方便。出事的时候，往往撤不回：数据写错了没有快照、业务高峰时重启丢了正在采集的数据、一条带口令的命令进了日志。

## 理念

- **只读和写入分两条路，各有入口。** 查数据随时可以，而且用只读账号查；改数据要走专门的流程。
- **凡写线上数据，都走写入流程**（第 5 章风险加码里的「写生产数据走专门流程」指的就是它）。写入要口令，而且口令只对摆出来的那一版方案有效，「可以」「跑吧」都不算。
- **部署只有一个入口，门槛写在脚本里。** 不许用任何热修方式绕开它。
- **业务高峰默认不动线上。** 写数据没有例外；部署要越过高峰窗口，只能由人明确同意，并写清这次要付出的代价。窗口值只有一个真源，现取，不照抄。
- **凭据不出现在对话、命令行参数、日志和提交里。**
- **自动化动作要登记，并且要少。** 能自动重启什么、不能自动重启什么，事先写清楚。
- **上线后的验证列成带日期的清单**，到期自动提醒，而不是靠记得。

## 怎么落地

### 只读查询：两条通道

推荐两条通道都用**只读角色**，区别只在能读多少：

| 通道 | 给谁用 | 推荐的限制 |
|---|---|---|
| 主会话通道 | 你自己和主会话 | 只读角色，可以读全部业务表；写入只走下面的写入流程 |
| 审查员只读通道 | 审查子代理、命令行审查（第 7 章） | 权限更低的只读角色，敏感类的表（账号、支付、用户私有内容）不授权；服务器侧限制这个账号只能执行一个固定的查询入口 |

坦白说，作者项目里主会话这条通道目前用的是能写的业务账号，「只查不写」只靠规则约束。第 2 章说过，文字规则不是强制机制，所以这里推荐的做法比作者项目的现状更严。

**最小的只读设置。** 只读角色（下面的 SQL 在本地 PostgreSQL 18 的事务里实测过语法）：

```sql
CREATE ROLE ro_reader LOGIN;                                  -- 口令另设，不写进脚本
ALTER ROLE ro_reader SET default_transaction_read_only = on;  -- 默认只读事务
ALTER ROLE ro_reader SET statement_timeout = '15s';           -- 防止大查询拖垮线上
GRANT CONNECT ON DATABASE <库名> TO ro_reader;
GRANT USAGE ON SCHEMA public TO ro_reader;
GRANT SELECT ON <允许读的表>, <允许读的表> TO ro_reader;       -- 只授要读的表，敏感表不授
```

`default_transaction_read_only` 只是默认值，会话里可以改掉；真正挡住写入的是「只授了 `SELECT`」。

在它外面包一层查询入口，比如一个脚本：

- 从标准输入读一条 SQL，只接受 `SELECT`、`WITH`、`EXPLAIN` 开头的语句，一次一条；
- 用只读角色连库执行，加上超时；
- 审查员那个账号用 ssh 的强制命令（`authorized_keys` 里的 `command=` 选项）绑定到这个入口，登录后只能执行它。

第 3、7 章示例里的 `/db-readonly` 技能，就是教 agent 怎么调用这个入口：什么时候查、一次查一条、结果附上查询语句和时间。

几条写法：

- **SQL 写进临时文件，传上去再执行。** 在 ssh 命令行里嵌套引号，再加上中文列名，会踩好几层转义。
- **口令不进命令行参数、不进连接 URL。** 用口令文件（PostgreSQL 的 `.pgpass`，权限设为 600），或者只在这一条命令里设的临时环境变量。命令行参数会出现在进程列表和 shell 历史里；更隐蔽的是**失败时的异常拼接**：一些语言的子进程库在命令失败时，会把整条命令行（含明文口令）拼进报错，随工具输出发出去。
- **本地那边更危险。** shell 里继承的数据库连接变量，可能正指向线上的隧道。这时你以为的「本地试跑」，就是在线上真跑。动手前先确认当前生效的是哪个库。

### 写线上数据：授权加六步

**授权（第 0 步）。** 先把方案摆给人：脚本或 SQL、写入范围（哪张表、什么条件）、预估影响行数、快照表名、回滚方式、计划执行时刻。人回复约定的口令（比如「确认方案」）之后才执行。其他说法一律再问一次。方案里任何一项变了，就重新摆、重新要口令。部署的确认口令不等于写库的授权。

**1. 非生产库完整试跑。** 记下输出和耗时。试跑只证明「脚本能跑通」，不证明「线上的结果对」，后者靠第 2、5 步。

**2. 只读量影响面，写好回滚。**

- 数两组数：写入范围内**现有**的行数（第 3 步拿它对快照），以及预估影响的行数（第 4、5 步拿它对实际）。起止边界日各单独数一次。
- 查残留：同名快照表、上次中断留下的半成品。有就先停下报告。
- 列出会写同一批表的其他写入者（定时任务、采集进程），执行时刻避开它们。
- 列出从这批表派生出来的快照表：源表改了，派生表不会自己跟着变。逐张写明「重算或不重算，理由是什么」。
- 避开业务高峰。
- **执行之前就写好回滚 SQL，并在非生产库演练一次。**

回滚的做法是「范围内整段删除，再把快照整行写回」，插入、更新、upsert 都适用。预期删除行数 = 快照行数 + 写入时新增的行数 − 写入时删除的行数，写成字面量；不要拿同一条 WHERE 现数出来的结果当预期，同源数出来必然相等，拦不住范围写错。

```sql
-- rollback.sql：不写 BEGIN / COMMIT，事务由外面给
DO $$
DECLARE n_del bigint; n_ins bigint; n_snap bigint;
  n_del_expect constant bigint := <预期删除行数>;
BEGIN
  SELECT count(*) INTO n_snap FROM <表>_bak_<日期>;
  DELETE FROM <表> WHERE <与快照相同的范围条件>;
  GET DIAGNOSTICS n_del = ROW_COUNT;
  IF n_del <> n_del_expect THEN
    RAISE EXCEPTION '删除 % 行，预期 % 行，整体回滚', n_del, n_del_expect;
  END IF;
  INSERT INTO <表> SELECT * FROM <表>_bak_<日期>;
  GET DIAGNOSTICS n_ins = ROW_COUNT;
  IF n_ins <> n_snap THEN
    RAISE EXCEPTION '写回 % 行，快照 % 行，整体回滚', n_ins, n_snap;
  END IF;
END $$;
```

照抄之前先确认三件事：没有别的表用外键引用这张表（否则整段删除会级联或被拦）；快照之后这张表没有加减列、没有调列序（`INSERT … SELECT *` 按位置对应，列序变了可能静默写反）；写入之后没有别的写入者碰过这段范围（整段删除会把它们写的也抹掉）。

**演练**用一个单独的 `drill.sql`，**每条命令单独一行**：

```sql
BEGIN;
\ir write.sql
SELECT …;            -- 看写入后的效果
\ir rollback.sql
SELECT …;            -- 看回滚后是否回到原样
ROLLBACK;
```

用 `psql -v ON_ERROR_STOP=1 -f drill.sql` 跑。两个要点：

- psql 的 `\ir` 这类元命令会把同一行后面的内容都当成它的参数。如果写成一行（`BEGIN; \ir rollback.sql; SELECT …; ROLLBACK;`），后面的查询和 `ROLLBACK` 会被**静默忽略**，只打几行警告（在 psql 18 上实测）。
- 被 `\ir` 引入的文件里不能有 `BEGIN` / `COMMIT`，否则里面的 `COMMIT` 照样会提交。
- 这个模板在本地用临时表实测过：写入后数据变化，回滚后恢复原样，预期行数写错时报错中止。

**3. 快照。**

- `CREATE TABLE <表>_bak_<日期> AS SELECT * FROM <表> WHERE <与写入相同的范围条件>;`
- **取全部列，不挑列**：挑出来的列，回滚不了其余的列。
- 快照和写入用**同一条 WHERE**。但同一条 WHERE 只保证两者一致，不保证这条 WHERE 本身对，所以建完以后要查快照的最小日期、最大日期、起止两天各自的行数、总行数，逐项对第 2 步的数。不符就停。
- 日期条件写成日期字面量，不要用带时区的时间戳参数去比（见下文「踩过的坑」）。
- 夜间整库备份代替不了它：整库恢复会把之后写入的数据一起回滚掉（推断，未演练）。

**4. 执行。**

- **代码里的回填、重算脚本**：线上跑的必须是**已经部署上去**的版本，不许单独拷一个改过的脚本上去跑。
- **一次性的手写 SQL 文件**：可以传上去执行，但内容必须和第 0 步摆出来的那一版完全一致（可以附上文件哈希，让人核对）。
- 完整输出落盘：对账的数字只会出现这一次。
- 手写 SQL 把预期行数写进 SQL 本身，写在 `DO` 块里：

  ```sql
  DO $$
  DECLARE n bigint;
  BEGIN
    UPDATE <表> SET … WHERE <范围条件>;
    GET DIAGNOSTICS n = ROW_COUNT;
    IF n <> <预估行数> THEN
      RAISE EXCEPTION '预期 <预估行数> 行，实际 % 行', n;
    END IF;
  END $$;
  ```

  用 `psql -v ON_ERROR_STOP=1 --single-transaction -f write.sql` 执行：任何一处不符就报错，整个文件回滚。（`--single-transaction` 在**正式执行**时正是你要的：全成功才提交。它不能用来演练，见下文「踩过的坑」。）

**5. 对账。**

- 前后对比：行数、变化分布、业务不变量。和预估不符就停：不重跑、不删快照，把差异报给人。
- **至少走一条独立于脚本自身的复算路径。** 脚本自带的对账和写入共用同一个范围条件，同源不构成证据（第 11 章）。

**6. 收尾。** 快照保留到人确认对账结果之后，再按精确表名删除，并确认没有残留；在对应 spec 的记录节写下执行时刻、命令、对账数字、快照表名与删除时刻。

不适用于结构变更：改表结构走数据库迁移，随部署上线。

### 部署：唯一入口

- **只有一个部署脚本可以上线**，门槛写在脚本的第一步（第 2 章）。作者项目里的门槛包括：测试通过、工作区干净、人明确确认、不在业务高峰。这里列出来只为说明，你的项目以脚本为准（第 4 章）。门槛不过就退出，绝不碰服务器。
- **禁止绕开脚本**：直接把构建产物同步到服务器、ssh 上去拉代码重启、在小内存服务器上现场构建，都不行。发现有人这么做，停下来提醒。
- **确认口令带上档位**。人一句话同时给出「确认」和「测试在哪跑」，agent 不必再追问：
  
  | 口令 | 含义 |
  |---|---|
  | 「确认部署，本地测」（默认） | 本地真跑一遍等价测试再部署 |
  | 「确认部署，走 CI」 | 先触发线上 CI，等结论成功再部署 |
  | 「确认部署，免测」 | 不跑测试门槛，其余门槛照查 |
  
  只说「确认部署」就走默认档；「不走 CI」有歧义，按本地测处理并说明，不擅自升级成免测。
- **确认只对当前提交有效。** 确认之后又改了代码，要重新确认。
- **脚本的确认参数买到的是可见性和摩擦，不是授权证明。** agent 完全可以自己加上「已确认」参数。想让机器落实「人确认过」，只能用 `ask` 这类必须由人亲手点的机制（第 10 章的令牌门槛就是这么做的），而且它也只防疏忽。别因为门槛过了，就以为已经获得授权。
- **业务高峰窗口默认不部署。** 窗口值只住在部署检查脚本里，现取，不照抄（第 4 章）。真要在高峰里部署（比如紧急修复），由人明确同意，同时写清代价：这一次重启会让哪些正在采集的数据丢失。脚本为此留一个单独的越过参数，用之前必须先问人。

### 自动化动作：少而登记

作者项目里的约定：

- 全链路只有一处脚本允许自动重启应用进程（内存超限时）；
- **数据库永不自动重启**；
- 自动体检和告警分流只产出文字，没有执行权；
- 新增任何自动化动作，先登记进部署手册（第 8 章）里的允许清单，再上线。

### 敏感数据

- 永远不把 `.env` 这类文件的内容回显到对话里。需要引用配置时，只说 key 名，不说 value。
- 数据库口令、密钥、服务器私钥，不写进代码、提交说明、日志。
- 在仓库里发现硬编码的凭据，**先告诉人，不要自动「修」成环境变量**：凭据可能已经泄露、需要先轮换，悄悄改掉反而掩盖了问题。

### 线上验证待办

上线之后的验证，很多要等到特定的时点才能做：第二天收盘后、连续三个交易日、某个月底。把它们列成清单：

- 每条写清**最早哪天、什么时段**可以验，验什么，用什么判据。
- 会话开场的 hook 读这份清单，报出「到期了几条、最早一条过期了几天」，提醒你决定要不要现在处理。
- 能自动取数的条目，由服务器上的一个定时取数脚本到点取数、留下证据；**判定仍由 agent 做**：核对时间窗、前提和判据对不对得上，再把结论写进清单、勾掉这一条。某条检查第一次这样判定时，agent 要另写一个**独立的查法**重取一次，同源的一致证明不了取数口径是对的。

## 代价与适用条件

- 写入流程很重。凡写线上数据都要走：授权、快照、对账三步任何时候都不能省；小范围、能回滚的修数，第 2 步的清单可以按实际情况裁剪。
- 只读通道、口令、门槛脚本都要先搭好。起步时至少做到三件事：查线上用只读账号、改线上先建快照、部署只走一个脚本。
- 「业务高峰」要按你的业务定义：电商的大促、教育的上课时段、作者项目里的交易时段。

## 踩过的坑

### 高峰时段部署，两天的数据永久缺失

有几类数据由应用进程在业务时段实时采样后写入，而它们依赖的原始数据保留期很短。连续两天在业务时段部署，重启掐断了采样，这部分数据永久缺失，事后也无法重建。

**修法**：部署检查脚本加一道「业务高峰窗口」门槛，窗口值只住在脚本里；越过它要人明确同意，并写清代价。

### 以为在演练回滚，其实提交了

为一次线上写入预先演练回滚 SQL，目标是本地库。用的是 `psql --single-transaction -f rollback.sql`，以为「跑完会回滚」。实际上 `--single-transaction` 只是把整个文件包进一个 `BEGIN … COMMIT`，跑完照样**提交**。偏偏回滚 SQL 里也没有预期删除行数；而事先用来证明护栏能拦住错误的那次反例测试，又把方向写反了，护栏其实没起作用。结果本地一张表里近 13 万行原有数据被删掉，外加 5 千多行试跑数据（线上没受影响）。

**修法**：演练一律用上面那个分行写的 `drill.sql`，包在 `BEGIN … ROLLBACK` 里；回滚 SQL 写死预期删除行数，不等就抛异常。

### 快照只取了几列，WHERE 还漏了一天

一次修数，快照只挑了 7 列，回滚时其余的列（比如算法版本、计算时间）就回不去了。同一次里，快照和脚本对账共用的那条日期条件，一起漏掉了起始日：数据库会话的时区是东八区，`DATE '2026-09-08' >= TIMESTAMPTZ '2026-09-08 00:00:00+00'` 为假，起始日整天被排除。两边一致，所以都没发现，最后是独立复算才查出来。

**修法**：快照取全部列；日期条件写成日期字面量；建完快照逐项核对最小、最大日期和起止日行数。

### 让用户在自己的终端请求线上接口，把自己的 IP 封了

线上有自动封禁：脚本发出的请求会被当成爬虫。agent 自己的请求被本机的 hook 拦下，hook 的提示写着「请用户在自己的终端执行」，于是 agent 请用户在终端里请求了一次线上接口。用户的终端和 agent 走的是同一个网络出口，IP 立刻被封，只能手动解除。

**修法**：

- 需要匿名请求线上接口时，在服务器本机上发起，不经过公网出口；自动化浏览器访问线上，按项目规定的豁免方式走。
- hook 的拦截提示不能引导人在本机终端代跑被拦的请求：那等于把同一个风险转给了人。
