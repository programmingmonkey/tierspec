# 第 4 章 · 唯一真源

## 遇到的问题

规则一多，自然就想「方便一点」：入口文件里抄一段要点，活文档里再列一张表，脚本注释里也摘几句。每一份副本在写下那天都是对的。

然后某一天改了规则，改了三处，漏了一处。agent 读到漏掉的那一处，照着旧规则做了，而且做得理直气壮：它确实是照规则做的。

## 理念

**一条规则只住一处。别处需要它，只写「在哪」，不写「是什么」。**

- **副本一定会漂。** 不是「可能」，是时间问题。同一个事实写在两处，改的人只要漏一处，两处就开始各说各的；agent 读到哪份，就信哪份。
- **指路比摘抄好维护。** 路径变了，引用会断，断了能被发现；内容变了，副本不会报错，只会悄悄变成假话。
- **文档里写「怎么现测」，不写会变的数。** 「检查项一共 12 条」写下去就会过时；写「现测：`grep -c '^check_' .githooks/pre-commit`」就不会悄悄过时。

## 怎么落地

### 分清「真源」和「指路」

| 内容 | 真源住在哪 | 别处怎么引用 |
|---|---|---|
| 规则正文 | 一份规则文件或技能文件 | 写路径，必要时写到节名 |
| 门槛的检查项与判据 | 实现门槛的脚本本身（头部注释） | 写「门槛在哪个脚本、怎么现测」 |
| 配置值（窗口时间、阈值） | 读它的那段代码或那份配置 | 写变量名与文件名，不抄值 |
| 现状（架构、数据流） | 活文档（第 8 章） | 写文档路径 |
| 当时为什么这么定 | spec 与事故记录 | 写文件名 |

入口文件 `CLAUDE.md` 是最容易长成「第二份规则」的地方。它只该有三类内容：送达路径说明、动作触发表、大文件读法（第 3 章）。

### 唯一受控的例外：生成，而不是手抄

有时确实需要一份汇总，比如一张「前端有哪些工程契约（第 9 章：能对着仓库判对错的不变量）、各自什么时候触发」的索引表。这种汇总**用脚本从真源生成**，不手写（下面是示意命令，脚本要自己写）：

```bash
python3 scripts/gen-index.py --write   # 从各契约文件现取「触发」与首句，重写索引里的生成块
```

再加一条自测：索引里的生成块必须和生成器的输出逐字一致。契约改了却没重新生成，提交就过不去。

### 用机器守住映射与加载链

规则文件、入口文件、触发表、读规则脚本之间有一张映射：哪份规则从哪条通道送达、哪个 topic 对应哪个文件。这张映射会漂，所以用自测守住，挂进 pre-commit：

- 入口文件里列的按路径规则清单，和 `.claude/rules/` 里实际带 `paths:` 的文件一致；
- 触发表里提到的每个 topic、每个技能都真实存在；
- 开场常驻的总量没超上限；规则文件里没有 `@` 导入；
- 活文档都在文档地图里登记了。

要清楚它的边界：**机器守的是「映射与加载链不坏」，管不了「内容对不对」。** 规则语义写错了、改了一条规则而别处的旧说法没跟着改，这类问题机器判不了，要靠下面的定期体检。

### 改完规则查矛盾

改了规则的规定（不只是措辞或挪位置），提交前对改过的文件跑一次跨文件一致性检查。较新版本的 Claude Code 内置了 `/doctor prompt-audit <路径>`，能报出跨文件矛盾和过时事实（如果你关掉了内置技能，它可能不可用；以你所用版本为准）。逐条核实后再改；矛盾里较旧的那句如果是禁令或安全规则，交给人来定，不让 agent 自己挑一边。

### 规则的增删门槛

唯一真源解决「一条规则住几处」，还要管住「规则有几条」。规则只增不减，常驻上下文就会被稀释：越长，每一条被遵守的概率越低。

**加一条规则之前，三条都满足才加：**

1. **不显而易见**：读代码、读活文档推不出来。架构描述、目录树、依赖清单不写成规则，它们会过时，agent 自己能读。
2. **犯过**：同一个错已经出现第二次；或者只出现一次，但代价大（数据永久缺失、凭据外泄、线上故障）。没犯过的「预防性」规则不加。
3. **写得具体**：能判对错（「用 X 不用 Y」「做 Z 前先跑 W」），并带一句理由。「注意」「小心」「尽量」不算规则。

**删规则**：逐条问「删掉它，agent 会犯错吗？犯了严不严重？」不会犯、或者犯了代价不大的先删，真犯了再按上面三条加回来。犯了会出事的留着。删之前先查它的来历（`git log -S`），别把当年用事故换来的规则删掉。

**强调要省着用**：🔴 和粗体只给真正被跳过过的那一条。处处都是红色，就没有一条是红色的。

## 代价与适用条件

- 指路意味着 agent 要多读一跳。对常用的规则，这一跳由送达通道（第 3 章）消化；只有偶尔用的规则才让它自己按路径去找。
- 守映射的自测要随规则体系一起长。起步时手工维护一张清单就够；规则文件超过十份，或者第一次出现「改三漏一」，再上自测。

## 踩过的坑

### 一套规则镜像，三份副本各自漂移

为了让不同的工具都能读到规则，曾经把规则从一个真源同步出几份镜像。没过多久，三份副本各改各的，互相矛盾，最后整套删除，回到「只住一处、别处指路」。后来复盘仓库里反复出现的「改三漏一」事故，根因全是同源副本。

### 照抄的门槛表漏了一项

部署门槛的检查项曾在文档里抄了一张表。后来脚本里新加了一项检查（本机已装依赖是否跟上锁文件），表里没跟着加。读文档的人以为门槛只有表里那几条。

**修法**：门槛的逐项判据只住脚本和部署规则，文档只写「门槛在哪、怎么现测」。

### 配置值在副本里漂成了旧值

部署时要避开的一个写入时间窗口，它的值在多处文档里各抄了一份。后来脚本里的值改了，几份副本还停在旧值。

**修法**：值只住读它的那段代码，文档写变量名。

### 分头改规则，旧说法没人跟着改

一次对全部规则文件做跨文件一致性检查，查出多条：时区相关的事实已经过时，还有一处规则仍写着允许在生产库上试写。都是分头改规则时，别处的旧说法没跟着改留下的。映射守卫全程是绿的，因为它本来就不管内容。
