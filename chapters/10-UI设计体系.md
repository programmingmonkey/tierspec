# 第 10 章 · UI 设计体系

## 遇到的问题

让 agent 写界面，最常见的两种结果：

- **一眼就是 AI 做的。** 每块内容都套一样的圆角卡片加淡阴影，卡片里再套卡片；渐变色大标题；一排「大数字 + 小标签」；每个标题前面一个图标；区块逐个淡入。单看都不难看，放在一个天天要用的工具里，全是噪声。
- **视觉慢慢漂移。** agent 找不到合适的颜色，就在组件里私设一个；下一个会话又私设一个相近的。几个月后，同一种「警告」可能就有了五种黄。

再加上第 9 章说过的那种情况：工程行为规则夹在视觉规范里，改样式的和改逻辑的都读得很累。

## 理念

**设计体系分层，每层只住一种东西；定死的轴照做，空着的轴才发挥。**

本章说的「人」，指项目的主人，也就是给 agent 拍板的那个人。

作者项目里，做界面时要守的东西落成了七层：

| 层 | 住什么 | 例子 |
|---|---|---|
| ① 令牌 | 颜色、阴影、间距等视觉取值，**值只住这里** | 样式文件里的 CSS 变量 |
| ② 视觉语言 | 风格意图：长什么样、为什么 | 总纲、原则、禁止项、「AI 默认长相」黑名单、正反样张 |
| ③ 主规范与页面覆盖 | 组件规范（尺寸、形态），以及每个令牌的名字、用途、用在哪；不抄令牌的值 | 主规范（大文件，按章读）；`pages/<页面>.md` 只覆盖主规范 |
| ④ 工程契约 | 代码必须怎么写 | 它不属于设计体系，和设计体系平级（第 9 章）；列在这里，只因为做界面时同样要守 |
| ⑤ 设计技能 | 工作方法：读哪份、按什么顺序干 | 探索、收敛、实现、审查四种模式 |
| ⑥ 审查模式 | ⑤ 里「审查」那种模式的细则 | 取证据加设计判断两路 |
| ⑦ 机器门槛 | 必须成立的那几条 | 令牌准入、硬编码颜色检查 |

三条贯穿的原则：

- **规则分两层：红线和风格原则。** 红线在任何阶段都生效，违反了必改（比如只用已登记的令牌；领域惯例不许反用，像行情软件里的「红涨绿跌」，红只能表示涨；工程契约）；风格原则在收敛和实现阶段才当标准，探索阶段只拿来标注「这个方案故意突破了哪几条、为什么」，不拿来删改方案。这个划分是在一次盲选失败之后才加上的，见下文「踩过的坑」。
- **主规范、视觉语言、页面覆盖，就是给 agent 的 brief（设计任务书）。** 借用 Anthropic 官方 frontend-design 技能里的说法：brief 定死的轴照做，空着的轴才发挥。「轴」指界面上可以独立变化的一个方面，比如色彩、字号、密度，见下文「轴表」。
- **新令牌先经人确认。** 找不到合适的令牌就停下来问人，不新增、不私设。

## 怎么落地

### 视觉语言：一份讲「为什么」的文件

主规范讲组件规范和令牌怎么用（这个按钮多高、哪个令牌用在哪），视觉语言讲意图。它的结构：

- **总纲**：这是什么产品、谁在什么场景下用、整体要什么感觉。作者项目的总纲第一条是「行业惯例优先」：惯例和通用设计原则冲突时，惯例赢。
- **原则**：每条标「层」（红线还是风格原则）和「适用」（整页、面板之间、面板内部、字段），并写清「怎么判」：满分什么样、违反什么样。
- **禁止项**：明确不要的风格。
- **AI 默认长相黑名单**：
  
  | 长相 | 为什么在工具型界面上不行 | 改成什么 |
  |---|---|---|
  | 每块都套一样的圆角卡片加淡阴影；卡片套卡片 | 容器套容器，只添框线噪声 | 用留白与浅分隔线分组 |
  | 渐变文字、渐变大标题 | 降低可读性，渐变本身不带信息 | 用字重或字号强调 |
  | 一排并列的「大数字 + 小标签」 | 大数字并列就没有焦点 | 一块最多一个焦点数字，并带基线 |
  | 彩虹色分类，每类一种鲜艳颜色 | 颜色一多，就没有颜色能表示重要；还会撞上语义色 | 先用文字区分，要用颜色时用弱强调 |
  | 每个标题、字段前面都放一个图标，或拿 emoji 当图标 | 不带信息的图标是噪声；emoji 各平台显示不一 | 只在图标表示操作或状态时用，统一一套图标库 |
  | 空状态只放插画、只写「暂无数据」 | 不说为什么空、能做什么 | 写清原因和下一步 |
  | 区块逐个淡入、数字从 0 滚动、刷新就重画 | 天天要看的界面上，装饰动效就是延迟 | 删掉，只留用户操作的短过渡 |
  | 卡片左侧的粗彩色竖条 | 最典型的 AI 长相，还会被读成告警 | 用文字、图标或字重表达 |
  
- **正反样张**：指出产品里哪一块是好例子、哪一块是反例，以及为什么。
- **已知冲突**：视觉语言和主规范冲突时，登记在这里交给人定，不默认任何一方赢。

### 轴表：哪些定死，哪些发挥

把界面拆成若干条「轴」，写清每个阶段每条轴是定死还是开放：

| 轴 | 探索期 | 收敛与实现 |
|---|---|---|
| 色彩与语义 | 开放（颜色强弱、分类色用不用），只守红线 | 定死 |
| 字体与字号 | 字体定死；字号在已登记的档里选 | 定死 |
| 间距、圆角、阴影 | 令牌内开放 | 定死 |
| 组件形态 | 开放：可以提新形态，收敛时和主规范的冲突交给人 | 定死 |
| 工程行为 | 定死（红线） | 定死 |
| 面板内的信息结构、焦点、字段取舍、空态文案、交互细节 | 开放 | 在原则范围内发挥 |

外部方法论只用在当前阶段开放或空着的轴上；和定死的轴冲突时，一律以自己的规范为准。

### 令牌准入：三道门槛

「不让视觉漂移」是项目主人定的规矩。只写成文字，agent 照样可能在找不到合适令牌时顺手加一个（第 2 章：文字规则不是强制机制），所以它落成了三道门槛：

1. **Claude 侧 hook**：`PreToolUse` 挂在编辑工具上，只盯两个文件：改令牌定义文件时新增或改动了令牌，或者在主题配置文件里新写了一个不是令牌的颜色值，就返回 `ask`，弹窗让人点允许。写法和第 3 章的最小实现一样，把 `deny` 换成 `ask` 即可。这是三道门槛里唯一能落实「人确认过」的一环，但它只覆盖编辑工具：agent 用 shell 命令改文件就绕过去了，所以它防的是疏忽，不是恶意（第 2 章）。
2. **pre-commit**：新增的令牌没登记进主规范、主题配置里新出现了非令牌的颜色值，拦。检查本身没跑成也拦。它只查「登记了没有」，查不了「人确认过没有」。
3. **lint**：扫所有改动的界面文件里的硬编码颜色、颜色函数字面量、私设颜色变量、emoji。前两道只盯令牌和主题文件，其余文件里的颜色靠它拦。

人确认之后，在同一个提交里新增令牌并登记进主规范，提交说明写「新增令牌 X，某日确认」。

几条机器管不到的（字体、圆角、动效、主次），靠交付前自查和审查。

### 四种模式

| 模式 | 什么时候 | 做什么 |
|---|---|---|
| **探索** | 新面板、新页面，或要重做一块 | 出 **3 个低保真候选**，每个只做默认态加两三个关键状态。候选之间至少在布局结构、信息编码方式、颜色强度这三个维度里的两个上明显不同，其中至少一个偏醒目、多用色。只守红线，风格原则只用来标注。交给人挑一个或组合几个 |
| **收敛** | 人挑定方向之后 | 出一版完整原型：覆盖全部状态，浅色、暗色两套。按全部原则自查；和风格原则冲突的不自动往克制的方向改，列给人定 |
| **实现** | 原型定稿之后 | 守主规范、页面覆盖和工程契约；浅暗两套都要看 |
| **审查** | 交付前自查；人叫时做完整两路 | 见下 |

和第 6 章 PRD 流程的关系：探索放在 PRD 的布局与口径问清之后；候选可以是低保真，但数据规模照线上量级造；收敛出的那一版，就是第 6 章「PRD 配原型」说的原型（单文件 HTML、真实规模的数据、演示开关）。改版时加新版本，不删旧版本：人挑完，落选的候选也留着。

### 审查：两路，报告结论先行

这里审的是界面本身，不是第 7 章审设计文档的那种评审。两路的分工也不一样：一路做确定性的取证，一路做判断，两者互补，而不是两个审查者做同一件事。

| 路 | 做什么 |
|---|---|
| **取证据**（确定性、可复现） | 浅色、暗色各截一张图，各跑一次无障碍扫描（axe）；跑设计 lint；按原型的演示开关逐状态截图；按主任务的操作流程做交互走查：键盘焦点、加载与失败态、可撤销、点击区域、表单出错、极端数据 |
| **设计判断**（独立子代理） | 只给它视觉语言、相关章节、截图和代码路径，**不给第一路的结论**；按视觉语言的每条原则打 0 / 1 / 2 分，每个分数带证据（截图位置或文件:行）；禁止项和黑名单只报命中与否 |

报告的格式是被项目主人「教」出来的（见下文「踩过的坑」）：

- **第一行是降级声明**：全跑到了写「全部跑到」，没跑成的写清哪项、为什么（比如暗色截图其实扫的是浅色页）。
- **紧接着是 3～5 条结论**：问题、在哪、建议，红线在前。读者只看这一块，也该知道要不要改、改哪里。明细放后面。
- **分数不设及格线**：分数用来对比和定位问题，不是门槛。

### 收录上游方法论：锁版本，看差异再更新

外部的设计方法论（比如官方的前端设计技能、社区的动效删减方法）很有用，但它们不是为你的产品写的。作者项目的做法：

- 原文收进 `upstream/` 目录，一字不改；在一个 LOCK 文件里登记来源仓库、commit、每个文件的 sha256。
- 另写一份 OVERLAY，逐节判「照用 / 改写 / 不适用」，agent 只读判为照用、改写的那几节。
- 原文文件不叫 `SKILL.md`，免得被注册成独立技能。
- 更新时先拉下差异给人看，人点头才替换；手改原文或 LOCK，自测会判红。
- 保留原作者的许可证；另写一份 NOTICE，说明每份原文的来源与收录方式。

## 代价与适用条件

- 七层是一个长期维护的产品逐步长出来的。起步时，一份令牌文件、一份写着「红线」和「黑名单」的短视觉语言、一条硬编码颜色的 lint，就能挡住大部分问题。
- 探索期出 3 个候选，比直接出一版慢得多，只在新面板、新页面上用。
- 完整的两路审查一次要截图、扫描、派子代理，只在人叫的时候做。

## 踩过的坑

### 新流程在盲选里输了

新的设计流程（视觉语言 + 设计技能）建好之后，拿一个真实面板和旧流程做了一次盲选：两边各出一版原型，去掉来源痕迹、随机标 A、B，对应关系封存、只公布哈希，由项目主人盲选。盲选分两轮：先只看两版原型选一次，再看过参考审查报告后定最终选择。两轮都选了旧流程那一版。

复盘时分了来源：

- 〔项目主人的理由，转述〕旧流程那版胜在：柱子里直接写着数字；不同状态有颜色区分；核心判断带颜色标签；一个关键操作做成了开关。
- 〔推断〕这几点里有两点，正是新流程按视觉语言的规则主动去掉的（不用运营在后台配置、随数据下发的业务色；颜色只表示涨跌），审查也把它们判成了问题；「柱子里写数字」被新流程挪进了浮窗。所以输的主要原因看起来在规则本身太克制，不在工具链。
- 〔事实〕两条流程各审了两版，一共四份参考审查报告，每份 13～17 KB，都没有一页结论。
- 〔项目主人原话〕「这四份审查内容太多，我找不到重点，我没有仔细看」。
- 〔推断〕参考审查报告对这次选择没起作用。

只有一个面板、一次盲选，算不上定论。项目主人看完复盘，决定继续用新流程，但要按复盘调整，原话里有一句是「一开始设计可以偏开放一些」。之后改了三件事：

1. **设计分探索、收敛、实现三段，开放度逐段收紧**：探索期出几个差别很大的候选给人挑。本章的四种模式就是这样来的。
2. **规则分成红线和风格原则两层**：探索期只守红线，风格原则只用来标注，冲突交给人定，不自动往克制的方向改。人一再选择突破同一条风格原则时，改这条原则本身。
3. **审查报告结论先行**：第一行降级声明，紧跟 3～5 条结论，明细放后面。

**教训**：设计规范是在替人做取舍。规范和人的实际偏好冲突时，要改的是规范，而且要有办法发现这种冲突，比如这次的盲选。
