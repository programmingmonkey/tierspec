# 第 1 章 · 文字规则不是强制机制

## 遇到的问题

刚开始用 AI 编码时，最自然的做法是把规矩写进 `CLAUDE.md` 或规则文件：「部署前先跑测试」「不许改已提交的 migration」「主分支不许直接推」。写得越来越多，也越来越有安全感。

然后某一天，规则写得清清楚楚的事，还是发生了。

## 理念

**规则文件不是配置，它和一段提示词是同一类东西：往上下文里塞文字，靠模型自己遵从。**

模型多数时候会遵从，但「多数时候」不够。下面这些情况，文字规则会悄无声息地失效：

- 换了一个会话、一个子代理，或者上下文被压缩，规则没被送到；
- 规则送到了，但当时的任务把注意力带走了；
- 规则互相打架，模型挑了一条。

所以要把规则分成两类：

| | 文字规则 | 机器门槛 |
|---|---|---|
| 是什么 | 上下文里的说明 | 不过就拦下的检查 |
| 适合管 | 判断、取舍、写法偏好 | 撤不回的动作、会静默出错的事 |
| 例子 | 「改动前先调研影响面」 | git 钩子、lint、测试、部署前检查脚本 |

判据只有一句：**这件事做错了，事后撤得回来吗？撤不回、或者错了没人会发现，就不能只靠文字。**

## 怎么落地

### 强制手段按强度排

1. **git 的 pre-commit 钩子**：任何环境下 `git commit` 都会触发，不依赖 CI 有没有跑、有没有额度。个人项目里通常是最强的一道。
2. **部署前检查脚本**：放在部署脚本的第一步，不过就 `exit 1`，绝不碰服务器。
3. **lint 与测试**：包括扫源码的断言，比如「这一层不许 import 那一层」。
4. **CI**：最后一道，但个人项目常因额度、触发条件而不跑。

### 最小示例：主分支保护

```bash
#!/bin/bash
# .githooks/pre-push —— 拦对 main 的强推与删除
while read -r local_ref local_sha remote_ref remote_sha; do
  if [ "$remote_ref" = "refs/heads/main" ]; then
    if [ "$local_sha" = "0000000000000000000000000000000000000000" ]; then
      echo "禁止删除远端 main" >&2; exit 1
    fi
    if [ "$remote_sha" != "0000000000000000000000000000000000000000" ] \
       && ! git merge-base --is-ancestor "$remote_sha" "$local_sha"; then
      echo "禁止强推 main" >&2; exit 1
    fi
  fi
done
```

启用：`git config core.hooksPath .githooks`。

### 介于两者之间：「先读后做」门槛

有些规则太长、太依赖判断，没法写成检查，但又重要到不能指望模型想起来（比如部署流程、git 分支模型）。可以用 Claude Code 的 `PreToolUse` hook 做一道中间层：

- agent 在一个会话里**第一次**要提交、推送、部署时，先拦下，要求它整份读完对应的规则；
- 读完之后（用 `PostToolUse` 确认真的读到了结尾）再放行同类动作。

这道门买到的是**可见性和摩擦**，不是授权证明——它保证模型动手前规则在上下文里，不保证它照做。真正的硬门槛仍然是上面那几道。

## 代价与适用条件

- 机器门槛要维护：判据会过时，误拦会训练出「红了也不用管」的习惯。只给撤不回、会静默出错的事上门槛。
- 门槛自己坏了怎么办要提前想好。「先读后做」这种辅助性门槛，判定器出错时应该放行并告警，否则一个 bug 能让 agent 一次提交都做不了；部署检查这种硬门槛则应该失败即关闭。
- hook 也不是不可伪造的：能改自己配置的 agent，也能改自己的 hook。它防的是疏忽，不是恶意。

## 踩过的坑

### 只写在规则里的门槛，覆盖为零

部署规则里写着三条门槛，平时一切正常——因为平时用的会话都读得到那份规则。后来一个读不到规则的会话去部署，三条门槛全部没有生效，而且没有任何报错。

**修法**：把三条门槛写进部署脚本的第一步。规则文件只说「门槛在哪个脚本」，不再逐条列判据（照抄的列表会漏项）。

### 护栏存在 ≠ 护栏生效

一个格式检查 hook 被当成唯一的强制兜底，先后四次失效：匹配条件永远不命中、内联脚本被 shell 吃掉、写死的字段名取不到路径、手写的判据从来没和权威实现对照过。**每一次都没有任何信号**——「没跑」和「判对了」的症状一样，都是安静。

**教训**：

- 护栏要带自测：构造一个真实输入跑一遍，钉进 self-test，并把 self-test 挂进 pre-commit。
- 先写反例：检查函数还不存在时自测应该判红，确认它真的能红，再写实现。
- 手写重实现的检查器，要定期和权威实现做差分。「它跑起来了」不等于「它判得对」。
- 新检查一上线就大片红时，先验证检查器本身，再归因到存量。
