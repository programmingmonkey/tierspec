# 第 6 章 · PRD 到 Spec

## 遇到的问题

个人开发者最常见的写法，是把一句想法直接丢给 agent：「加一个面板，展示题材的轮动关系。」agent 会很快交出一份看起来完整的 spec，甚至直接开写代码。

问题出在那份 spec 里混着三种东西：

- 你**真正想要的**（意图）；
- agent **替你猜的**（默认值、口径、边界情况）；
- agent **顺手定的技术方案**（表、接口、缓存）。

三者搅在一起，你在 review 时分不清哪句是你说的、哪句是它猜的。等做完才发现，一个关键口径是它猜错的，而且已经写进了表结构。

## 理念

**C 档的产品需求，尽量先出 PRD、配一份原型，再转 Spec。PRD 管「要什么」，原型管「长什么样」，Spec 管「怎么做」。**

- **PRD 只写用户看得见、能验收的行为。** 技术方案一律不进 PRD；agent 讨论时发现的技术约束，只有影响产品取舍的才写，而且写成「代价是用户会看到 X」。PRD 里出现的技术数值都只是建议，以 spec 的设计为准。
- **人写意图，agent 补全与追问。** 背景、目标、范围、功能列表，以及每个功能下的原始需求（布局、内容、交互等【】各项）由人写；其余由 agent 补全。agent **不改人写的原文**，补充写在原文下方，歧义一律变成确认事项。
- **每个歧义都要有人拍板，并留下原话。** 确认事项分三栏：告知、已确认、待确认。已确认的每条保留人的原话，以后有争议能回到原话。原话只是选项代号（「选 A」「选 2」）时，定案栏要把被选中的那个选项写全，否则日后查回原话也不知道选的是什么。
- **定案速查是 PRD 的出口。** PRD 最后一节把所有定案压成一句一条，spec 的需求从这里改写，逐条标出处。

### 什么时候出 PRD

| 档位 | 产品需求（用户看得到的行为变了） | 技术改造 / 缺陷修复 / 工程任务 |
|---|---|---|
| A | 不需要 | 不需要 |
| B | 不需要，spec 里引用用户原话即可 | 不需要 |
| **C** | **尽量先出 PRD + 原型**；新模块、新页面尤其要出 | 不需要，直接写 `requirements.md` |

PRD 不是门槛，是工具：C 档意味着有撤不回的步骤、要反复拍板的取舍，或需要留档审计，正是这类需求最怕意图被猜错。改动小、意图一两句就说得清的 C 档（比如给已有页面加一个字段的口径修正），直接在 spec 的需求里引用原话也可以。新模块、新页面不一样：它们的布局、状态、口径全是新的，没有 PRD 和原型，agent 只能猜。

## 怎么落地

### 一份 PRD 的生命周期

```
人写骨架（背景 / 目标 / 范围 / 功能列表 / 原始需求）
  ▼
agent 补全：核实现状基线 → 补口径、状态、边界 → 列待确认事项（🔴 阻塞 / 🟡 有默认建议）
  ▼
人逐条答复（在条目下写「答：…」，🟡 可以只回「按建议」）
  ▼
agent 把答复迁入「已确认」、回填正文；带出新问题就开下一轮
  ▼  （重复，直到布局与口径不再有 🔴）
原型：用接近真实规模的数据做一份能在浏览器里点的原型；原型带出的问题回到确认事项，再开一轮
  ▼
需求审查（由人叫，两路独立，见第 7 章）
  ▼
定案速查 → 转 spec → PRD 与原型归档
```

### PRD 配原型

PRD 用文字和字符画说「要什么」，原型用一张能点的页面说「长什么样」。两者配套，各管一半：

| | PRD | 原型 |
|---|---|---|
| 是什么的真源 | 意图、口径、规则 | 视觉：尺寸、列宽、间距、颜色、各状态的样子 |
| 谁先写 | 人写骨架 | agent 按 PRD 出，人挑方向 |
| 抓得住什么 | 歧义、漏掉的状态、同名不同义 | 真实数据规模下放不放得下、看不看得清、交互顺不顺 |

几条做法：

- **原型是一个单文件 HTML**，浏览器直接打开，不依赖项目代码。数据写死在文件里，规模照线上量级造（几十天、几十条），不要只放三五条好看的样例。
- **把 PRD 里需要人看一眼的状态做成可切换的演示开关**：正常、空态、加载中、刚上线全空……数据里自然会出现的状态（比如某天缺数据）不必单做开关，但在原型说明里写明哪些状态没做。开关的名字用 PRD 的条目号或验收编号，后面逐状态截图对照实现时一一对得上。
- **浅色、暗色两种主题都要看**，对比度不达标在原型阶段就要暴露。
- **原型推翻 PRD 是好事**，但必须回到确认事项重新拍板、回填正文，不能只改原型。
- 配套示例：[原型-题材天梯面板.html](../examples/原型-题材天梯面板.html)（数据为虚构）。

### PRD 的骨架

完整模板见 [templates/PRD模板.md](../templates/PRD模板.md)。各节的职责：

| 节 | 谁写 | 管什么 |
|---|---|---|
| 1 需求概述 | 人；现状基线由 agent 补 | 背景、目标、范围；agent 核实「现在已经有什么」，每条标来源与日期 |
| 2 功能列表 | 人起头，agent 补全 | 一行一个功能点，后面的阶段规划按它切 |
| 3 功能需求 | 人写【】各项，agent 在下方补充 | 布局、图例、口径、数据量与溢出、状态表、与已有概念的关系 |
| 4 非功能需求 | agent 起草，人确认 | 只写用户能验收的：时效、故障时看到什么、谁能看、等多久 |
| 5 UI/UX | — | 指向原型，原型是视觉真源 |
| 6 阶段规划 | agent 起草，人确认 | 每个阶段必须能独立发布，并答得出「谁来验、验什么」 |
| 7 确认事项 | 双方 | 告知 / 已确认（附原话）/ 待确认 |
| 8 定案速查 | agent | 一句一条，标出处，是 spec 的需求骨架 |

### 几条容易写错的规矩

- **口径表要逐个数回答。** 面板上的每一个数字、每一个标签，都要答出：含义是什么、按什么时点算、和哪个已有面板同口径。拿不准的写「?」，让 agent 去查。很多返工都来自「同名不同义」：同一个词，在别的页面里是另一个意思。
- **状态要按表填，不能只写正常态。** 数据未就绪、部分就绪、历史日、非交易日、上线前没有数据的日期、加载中、请求失败，每一行都要写「显示什么」。
- **现状基线必须核实，而且只是讨论依据。** 数据类结论查线上，不查本地。落 spec 时还要重新登记一遍证据，因为 PRD 写完到 spec 开工之间，现状可能已经变了。
- **确认事项共用一个递增号段。** 已确认和待确认两栏各自取号，迟早会出现同号指不同事，而正文里到处是「见 7.2-N」这样的交叉引用。新条目一律取「当前最大号 + 1」，迁栏保留原号。
- **阶段表不接受形容词。** 「基本完成」「主体可用」不算验收；写不出「能独立发」的阶段，就并入相邻阶段或重切。依赖还没上线的东西，单列一行「前置」。
- **不在 PRD 里加「不做」清单。** 范围由正文和定案界定。旧文档里的排除项，不能拿来否决新需求。

### 转 Spec

1. **从定案速查改写，不整段照抄。** spec 的每条需求标出处，例如「出处：PRD 定案 8-3」。
2. **原话保留原样。** 用户原话或 PRD 条目，引用时不改字；细化、补充另外标注。
3. **引用 PRD 只写文件名，不带目录。** PRD 做完会归档到别的目录，带目录的路径一归档就断。
4. **冲突时以 spec 为准，并回头订正 PRD。** spec 开工后发现的新事实，回填 PRD 的确认事项，免得两份文档各说各的。
5. **阶段表变成 spec 的分期表。** 需要拆成多套 spec 的，拆法与上线顺序写进主题 README（第 5 章「B 与 C 的结构」）。

## 代价与适用条件

- 一份认真的 PRD 要来回好几轮，几小时到一两天。只在 C 档用；A、B 档硬套 PRD，是把 SDD 最受诟病的「瀑布感」请回来。
- 需要人真的去答确认事项。人不答、或者一律「你看着办」，PRD 就退化成 agent 自问自答，比没有更危险，因为它看起来像定过案。
- PRD 是意图，不是现状。上线后它就是历史文档，判断「现在是什么样」看源码与活文档（第 8 章）。

## 踩过的坑

### 一句原始需求，背后是一个状态机

[案例](../examples/PRD案例-题材天梯面板.md)里，人写的原始需求只有十几行：横轴日期、纵轴等级，涨超 3% 升级、跌超 3% 降级。agent 补全时发现，「等级」是**累积状态**：今天的等级取决于昨天的等级。由此带出一串原文没写、但必须拍板的问题：

- 题材中途消失几天再回来，等级从哪算？
- 算法能不能把题材降到出局？
- 人工改了某一天的等级，之后的日期要不要跟着重算？

这些问题如果留给 agent 在写代码时自己猜，每一个都会变成表结构里的一个默认值。PRD 把其中大多数变成了四轮、二十多条有原话可查的确认事项。

但不是全部。「人工改了某天的等级，之后要不要重算」这一条，是 agent 在口径定义里提出、随一整组口径一起被确认的，没有单独的人的原话。照规范它本该单列成一条确认事项。案例里如实标出了这个缺口（定案 8-6），这也说明：规范写在那里，执行时仍会漏，所以才需要需求审查（第 7 章）。

### 原型会推翻 PRD

同一个案例里，原型初版只造了 12 个题材（线上要多得多），量出来的高度明显偏小；按线上规模重造后，面板高约 1745px，远超一屏，原定的「不折叠、不在等级槽内滚动」只能补一条例外。所以原型数据要照线上规模造。原型还证明了「下一交易日」那一列根本不需要。**PRD 定的是意图，原型验的是这个意图在真实数据下长什么样。** 两者冲突时，回到确认事项里重新拍板，而不是悄悄改一边。
