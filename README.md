# TierSpec

**从需求到实现，面向个人开发者的分档式 AI 工程规范。**

TierSpec 回答一个问题：一个人带着 AI 编码 agent，怎么在一个真实、长期维护的项目里，把一个想法从需求一路做到上线，而不把项目越改越乱。

它和常见的 Spec 驱动开发（SDD）一样，主张「先写清楚再动手」；不同在于：

- **分档，而不是一刀切。** 不是每个改动都要走完整流程。先只读调研、报四行，再定 A / B / C 三档：有撤不回的步骤、要反复拍板的取舍或要留档审计的，是 C；其余看「改法能不能一句话说清」「影响面核实过没有」，分 A 和 B。流程轻重跟着档位走。
- **C 档产品需求尽量先出 PRD，再转 Spec。** 新模块、新页面尤其要出；PRD 配一份原型，产品意图与技术方案分开写、分开审。
- **规则要送得到，关键动作要拦得住。** spec 只是一层；规则怎么送达 agent、撤不回的动作怎么用机器门槛拦，同样是规范的一部分。
- **结论要有依据。** 数据类结论查线上、证据逐条登记，没有可信依据时不产出。

本仓库只讲**理念与做法**，附模板与脱敏案例，不提供框架代码。工具以 [Claude Code](https://docs.claude.com/en/docs/claude-code) 为例，但大部分理念与具体工具无关。

## 全流程

```
想法
 │  只读调研，报四行：根因或目标 / 影响面 / 同类 / 改法
 ▼
定档 ── A 直接改 ──────────────────────────────────────────▶ 一次提交（四行写进提交说明）
 │
 ├──── B 轻量计划 ── 单个 spec.md（目标与不做 / 做法与步骤 / 记录）▶ 实现 → 验证
 │
 └──── C 完整 ──┬── 产品需求：PRD + 原型（尽量出）── 需求审查 ── 定案速查
                │                                         │
                │                                         ▼
                └── 技术改造 / 缺陷修复 / 工程任务 ──▶ requirements → design → tasks
                                                          │
                                                          ▼
                                       实现 → 代码审查 → 验收 → 上线后验证 → 归档
```

贯穿全程：规则分层送达（第 2 章）、机器门槛（第 1 章）、证据登记与认识诚实（第 10 章）。

## 怎么读

- 不必按顺序。先读第 0 章知道出处，再看「全流程」，挑你项目里正在疼的那一章。
- **照判据裁剪，别照抄规则。** 每条规则都写了它被什么问题逼出来；你的项目没有那个问题，就不需要那条规则。
- 规则体系是长出来的，不是一次设计好的。起步只需要三样：第 1 章的一个 git 钩子、第 4 章的「先报四行再定档」，加上一条认识诚实的底线：**数据类结论查线上，查不到就说查不到，不编**（第 10 章成稿后会展开）。需求变复杂了再加第 5 章。
