# Chapter 4 · Single Source of Truth

## The problem

Once there are a lot of rules, it's natural to want to "make things a bit easier": copy a summary into the entry file, list a table in the living docs, quote a few lines in a script comment. Every one of these copies is correct on the day it's written.

Then one day you change a rule, update three places, and miss one. The agent reads the one you missed, follows the old rule, and does so with total confidence: it really did follow the rules.

## The idea

**Each rule lives in exactly one place. Anywhere else that needs it says only "where it is," not "what it is."**

- **Copies will drift.** Not "might"; it's only a matter of time. When the same fact is written in two places, the person changing it only has to miss one, and the two start saying different things; the agent trusts whichever one it happens to read.
- **Pointers are easier to maintain than excerpts.** When a path changes, the reference breaks, and a break can be detected; when content changes, a copy raises no error, it just quietly becomes false.
- **Docs say "how to check live," not numbers that will change.** "There are 12 checks in total" goes stale the moment it's written; "Check live: `grep -c '^check_' .githooks/pre-commit`" doesn't go stale silently.

## In practice

### Separate the "source of truth" from the "pointer"

| Content | Where the source of truth lives | How other places reference it |
|---|---|---|
| Rule text | A single rule file or skill file | Give the path, down to the section name if needed |
| A gate's checks and criteria | The script that implements the gate (its header comment) | Say "which script the gate is in, and how to check live" |
| Config values (time windows, thresholds) | The code or config file that reads them | Give the variable name and file name; don't copy the value |
| Current state (architecture, data flow) | Living docs (Chapter 8) | Give the doc path |
| Why it was decided that way at the time | Specs and incident records | Give the file name |

The entry file `CLAUDE.md` is the place most likely to grow into a "second copy of the rules." It should hold only three kinds of content: a description of the delivery paths, the action trigger table, and how to read large files (Chapter 3).

### The one controlled exception: generate, don't copy by hand

Sometimes you really do need a summary, for example an index table of "which engineering contracts the frontend has (Chapter 9: invariants that can be checked right or wrong against the repo) and when each one triggers." This kind of summary is **generated by a script from the sources of truth**, not written by hand (the command below is illustrative; you have to write the script yourself):

```bash
python3 scripts/gen-index.py --write   # pull each contract file's "trigger" and first sentence live, and rewrite the generated block in the index
```

Then add a self-test: the generated block in the index must match the generator's output character for character. If a contract changes but the index isn't regenerated, the commit doesn't go through.

### Use machines to guard the mapping and the loading chain

Rule files, the entry file, the trigger table and the rule-reading script are tied together by a mapping: which rule file is delivered through which channel, which topic corresponds to which file. That mapping drifts, so guard it with a self-test hooked into pre-commit:

- The list of path-scoped rules in the entry file matches the files under `.claude/rules/` that actually carry `paths:`;
- Every topic and every skill mentioned in the trigger table actually exists;
- The always-on content at session start is within its total size cap; rule files contain no `@` imports;
- Every living doc is registered in the doc map.

Be clear about its limits: **what the machine guards is "the mapping and loading chain aren't broken"; it can't tell whether the content is right.** A rule whose meaning is wrong, or a rule that was changed while the old wording elsewhere wasn't updated to match: a machine can't judge these. They need the periodic checkup below.

### Check for contradictions after changing rules

When you've changed what a rule requires (not just its wording or where it sits), run a cross-file consistency check on the changed files before committing. Newer versions of Claude Code ship a built-in `/doctor prompt-audit <path>` that reports cross-file contradictions and outdated facts (if you've turned off built-in skills, it may not be available; go by the version you're using). Verify each finding before changing anything; if the older statement in a contradiction is a prohibition or a safety rule, hand it to the human to decide, and don't let the agent pick a side itself.

### The bar for adding and removing rules

A single source of truth settles "how many places a rule lives in"; you also have to keep "how many rules there are" under control. If rules are only ever added and never removed, the always-on context gets diluted: the longer it gets, the lower the chance that any one rule is followed.

**Before adding a rule, add it only if all three hold:**

1. **Not obvious**: it can't be inferred from reading the code or the living docs. Architecture descriptions, directory trees and dependency lists don't get written as rules; they go stale, and the agent can read them itself.
2. **It's happened**: the same mistake has now occurred a second time; or it occurred only once, but at high cost (permanent data loss, leaked credentials, a production incident). "Preventive" rules for mistakes that have never happened don't get added.
3. **Specific**: it can be judged right or wrong ("use X, not Y"; "before doing Z, run W"), and it comes with a one-sentence reason. "Be careful," "watch out" and "try to" don't count as rules.

**Removing rules**: for each one, ask "if I delete it, will the agent make the mistake? And if it does, how bad is it?" Delete first the ones where it won't make the mistake, or where the mistake is cheap; if it really does make the mistake, add the rule back under the three conditions above. Keep the ones where the mistake would cause real trouble. Before deleting, check its history (`git log -S`), so you don't delete a rule that was paid for with an incident.

**Use emphasis sparingly**: 🔴 and bold are only for the one rule that has actually been skipped. When everything is red, nothing is.

## Costs and when it applies

- Pointing means the agent has to read one extra hop. For frequently used rules, that hop is absorbed by the delivery channels (Chapter 3); only rarely used rules are left for the agent to find by path on its own.
- The self-test that guards the mapping has to grow along with the rule system. At the start, a hand-maintained checklist is enough; once you have more than ten rule files, or the first "changed three, missed one" happens, bring in the self-test.

## Pitfalls we hit

### A set of rule mirrors, with three copies each drifting on its own

To let different tools read the rules, we once synced several mirrors out of a single source of truth. Before long, the three copies had each been edited separately and contradicted each other; in the end the whole set was deleted, and we went back to "live in one place, point from everywhere else." Later, when we went back over the "changed three, missed one" incidents that kept recurring in the repo, every one of them traced back to copies of the same source.

### A copied gate table missed an item

The deploy gate's checks were once copied into a table in the docs. Later a new check was added to the script (whether the locally installed dependencies are up to date with the lockfile), and the table wasn't updated. People reading the docs thought the gate had only the checks in the table.

**Fix**: the gate's item-by-item criteria live only in the script and the deploy rules; the docs say only "where the gate is and how to check live."

### A config value drifted to an old value in the copies

A write time window that deploys must avoid had its value copied into several docs. Later the value in the script changed, and the copies were stuck on the old value.

**Fix**: the value lives only in the code that reads it; the docs give the variable name.

### Rules changed separately, and nobody updated the old wording

One cross-file consistency check over all the rule files turned up several problems: timezone-related facts had gone stale, and one rule still said trial writes on the production database were allowed. All of them were left behind when rules were changed separately and the old wording elsewhere wasn't updated to match. The mapping guard stayed green the whole time, because it never checked content in the first place.
